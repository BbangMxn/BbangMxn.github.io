# 回答の根拠を追跡するRAGバックエンド

趣味コミュニティを出発点に、検索結果と推薦の根拠をつなぐ処理フローを構築しました。

<div class="case-facts">Nazgul / 個人開発・研究プロトタイプ<br>担当: 画面、Spring Bootサーバー、ドメイン設計、ローカルAI実験、検証記録<br>技術: Java · Spring Boot · SQLite · Ollama<br>状態: 検索フローを検証、定量評価は今後拡充</div>

## 01. 課題 — 検索結果だけでは推薦理由を説明できない

趣味SNSのフィードと探索画面を実装した後、AIによる検索・推薦への拡張に取り組みました。しかし、既存のフィード構造では、回答に使われた情報を追跡する仕組みが不足していました。

そこで、機能追加よりも、趣味データの検索から回答の根拠までをつなぐ構造の検証に対象を絞りました。

## 02. 判断 — 趣味の文脈と選択過程を残す

- **Entity Card:** データをすぐに細かいチャンクに分けず、趣味の文脈を保つカード単位を設けました。
- **階層型検索:** カードから詳細な根拠へ進むことで、検索結果と推薦理由を結びつけました。
- **RecommendationTrace:** 候補の選択、遅延、失敗を確認できるように追跡記録を分離しました。

実際の質問で処理がつながることを確認する設計です。他の検索方式に対する品質の優位性を実証したものではありません。

## 03. 実装 — 入力から根拠までをつなぐ

**趣味データ → Entity Card → Chunk → Answer → Trace**

Spring Bootの検索サーバーとローカルAIの実験環境を構築。趣味選択・探索画面を検索と推薦につなげました。画面、サーバー、ドメイン設計、実験記録を個人で担当しました。

## 04. 検証 — 処理フローを確認、応答時間は改善課題

| 項目         | 観測結果                                       |
| ------------ | ---------------------------------------------- |
| データ範囲   | 趣味44件、9カテゴリ                            |
| 質問         | 러닝 초보 루틴（ランニング初心者のルーティン） |
| 返却結果     | カード3件、推薦投稿3件                         |
| 平均応答時間 | 60,531ms、約60.5秒                             |
| 確認した範囲 | Card → Chunk → Answer → Traceの接続            |

これは処理フローの動作確認であり、性能改善や本番環境での実績を示す数値ではありません。再現可能な評価には、試行回数・機材・モデルなどの測定条件の整理が必要です。
