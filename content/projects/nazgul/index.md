# 답변의 근거를 추적하는 RAG 백엔드

취미 커뮤니티에서 출발해, 검색 결과와 추천 근거를 함께 확인할 수 있는 흐름을 만든 프로젝트입니다.

## 01. 문제 — 검색 결과만으로는 추천 이유를 설명하기 어려웠습니다

취미 SNS의 홈 피드와 탐색 화면을 만든 뒤, 검색과 추천을 AI로 확장하려 했습니다. 하지만 기존 피드 구조만으로는 어떤 취미 정보가 답변에 사용됐는지 추적할 근거가 부족했습니다.

목표를 ‘커뮤니티 기능 추가’에서 ‘취미 데이터 검색과 답변 근거를 연결하는 구조 검증’으로 좁혔습니다.

## 02. 선택 — 취미 단위를 유지하고, 선택 과정을 따로 기록했습니다

- **Entity Card:** 취미 데이터를 바로 작은 청크로 나누기보다, 취미의 맥락을 유지하는 카드 단위로 먼저 구성했습니다.
- **계층형 검색:** 카드에서 세부 근거로 이어지도록 설계해 검색 결과와 추천 이유를 연결했습니다.
- **RecommendationTrace:** 결과뿐 아니라 후보 선택과 지연, 실패를 다시 살펴볼 수 있도록 추적 기록을 분리했습니다.

이 선택의 가치는 실제 질의에서 흐름이 이어지는지 확인하는 데 있습니다. 다른 검색 방식보다 품질이 우수하다는 비교 검증까지 완료한 상태는 아닙니다.

## 03. 구현 — 입력에서 근거까지 연결했습니다

### 아키텍처

**취미 데이터 → Entity Card → Chunk → Answer → Trace**

Spring Boot 기반 검색 서버와 로컬 AI 실험 환경을 구성하고, 취미 선택·탐색 화면을 검색 및 추천 흐름에 연결했습니다. 화면부터 서버, 도메인 설계, 실험 기록까지 1인 개발로 진행했습니다.

[구현 화면과 상세 구조](./implementation-notes) · [프로젝트 명세](./spec)

## 04. 검증 — 흐름은 확인했고, 응답 속도는 과제로 남았습니다

기존 실험 기록의 관찰 내용입니다.

| 항목           | 관찰 결과                          |
| -------------- | ---------------------------------- |
| 데이터 범위    | 취미 44개, 카테고리 9개            |
| 관찰 질의      | 러닝 초보 루틴                     |
| 반환 결과      | 카드 3개, 추천 포스트 3개          |
| 평균 응답 시간 | 60,531ms, 약 60.5초                |
| 확인 범위      | Card → Chunk → Answer → Trace 연결 |

이 결과는 검색 흐름이 동작한다는 근거입니다. 응답 속도의 개선 성과나 운영 환경의 성능 지표는 아닙니다. 반복 횟수·장비·모델 등 측정 조건을 함께 정리해야 재현 가능한 평가로 확장할 수 있습니다.

## 05. 다음 과제 — 같은 조건에서 비교할 수 있는 평가 만들기

질의별 지연 구간을 나누고, 더 큰 데이터셋과 정량 평가를 추가하는 것이 다음 과제입니다. 구조를 구현한 것과 검색 품질을 입증한 것을 구분해 기록합니다.
